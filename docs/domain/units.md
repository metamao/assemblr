# Units

A unit is an author-owned, opinionated implementation of a software capability
or integration. Units may target web applications, infrastructure, native
applications, services, or any other software. Assemblr is technology-agnostic.

## Identity — Approved

The canonical form of a unit identity is:

```text
@owner/unit-name
```

Examples:

```text
@metamao/node
@metamao/cloudflare-worker
@metamao/cloudflare-angular-ssr
@metamao/d1-drizzle
@alice/cloudflare-angular-ssr
```

Rules:

- The owner is mandatory.
- An owner may represent an individual or an organization.
- Unit names use lowercase ASCII letters, digits, and hyphens. Owners follow
  the same convention.
- Each segment, owner and unit name, is non-empty, begins and ends with a
  letter or digit, and contains no consecutive hyphens. For example, `-node`,
  `node-`, and `cloud--worker` are malformed.
- An identity is exactly `@`, the owner, `/`, and the unit name, with nothing
  else.
- A malformed identity is rejected with a validation error. It is never
  normalized, for example by lowercasing.
- There is no identity-specific length limit.
- Owner and unit name **together** determine identity.
  `@metamao/cloudflare-angular-ssr` and `@alice/cloudflare-angular-ssr` are
  different units. Neither is official or privileged.
- The unit's own manifest supplies its identity. Registries, catalogs, and
  repository locations do not.
- Identity does **not** imply dependencies. A unit declares its dependencies
  explicitly (see [dependencies.md](dependencies.md)).
- Do not infer repository layout, dependency structure, or relationships
  between units from owners or names. For example, `cloudflare-angular-ssr`
  does not imply a dependency on `cloudflare-worker`.
- The owner namespace is not necessarily tied permanently to a GitHub identity.
- Authentication and verification of namespace ownership are **not required in
  Alpha**.

Catalog identities use the same rules (see
[registries-and-discovery.md](registries-and-discovery.md#catalogs--approved)).

## Versioning — Approved

- Unit versions use SemVer.
- The manifest declares the unit's **exact** version.
- Dependency declarations may use SemVer **ranges**.
- Resolution and lock state record **exact** versions.
- Each published version is a Git tag, `v<version>`, whose manifest declares
  exactly that version (see
  [registries-and-discovery.md](registries-and-discovery.md#units-are-git-repositories--approved)).
- Published versions are immutable (see
  [authoring-workflow.md](authoring-workflow.md#publication--approved)).
- A unit's published versions are unique ignoring build metadata. Two versions
  that differ only in build metadata, such as `1.0.0+a` and `1.0.0+b`, are
  ambiguous, and Assemblr never prefers one of them because of its metadata
  (see
  [dependencies.md](dependencies.md#pre-releases-and-build-metadata--approved)).

Open:

- The SemVer range dialect. **OC-15.**
- Whether publication, registration, or synchronization reject versions that
  differ only in build metadata before resolution reports them. **OC-25.**

## Authoring repository convention — Approved

Every unit is maintained in **its own Git repository**. This is a requirement,
not just an organizational convention: Git holds the history from which
published versions are identified and historical content is recovered.

- A repository holds exactly **one** unit, with `manifest.jsonc` at its root.
  Several independently published units never share a repository.
- Each unit has an independent publication lifecycle.
- Repositories may be private. The owner decides how they are hosted and
  organized.

A unit repository has this conceptual structure:

```text
manifest.jsonc        required
src/                  optional: files introduced by the unit
amendments/           optional: modified copies of dependency files
.gitignore            contains /build/
build/                generated by `unit build`, Git-ignored
<local manifest schema>  generated, offline JSON Schema for editor support
<unit lockfile>       CLI-managed, tracked: resolved dependency versions
```

- `manifest.jsonc` is required.
- The unit lockfile is described in
  [authoring-workflow.md](authoring-workflow.md#unit-lock-state--approved).
- `src/` and `amendments/` are each optional. Do not require empty directories
  just for uniformity.
- The initialized scaffold supports editing the manifest with JSON Schema
  (see [manifest.md](manifest.md#editor-support--approved)).

Open:

- The file name and location of the generated local manifest schema, and
  whether it is tracked in Git. **OC-17.**
- The unit lockfile's name, location, and format. **OC-46.**

## Unit contents — Approved

### `src/`: unit files

`src/` holds the files the unit introduces. All files in `src/` follow the
same conceptual lifecycle. There are **no** author-facing file classes such as
the former `derived` and `scaffold` distinction, and they must not be
reintroduced.

Unit file contents may be customized by the unit's parameters through template
interpolation. Parameters never change file paths or file existence (see
[parameters-and-options.md](parameters-and-options.md#what-parameters-must-not-do--approved)).

In a consumer project, files delivered from `src/` are starting points that
the consumer may modify. They are reconciled like every other contribution
(see [consumer-projects.md](consumer-projects.md#file-contributions--approved)).

Path collisions:

- If two different units in one composition provide a file at the same path
  through their `src/` directories, composition fails with an explicit **path
  collision** error that names both units and the path.
- This holds whether the units are independent or one depends on the other.
  Neither unit wins by declaration order, dependency order, or any other
  priority, and the two files are never merged automatically.
- A unit that needs to modify a file a dependency provides does so through an
  [amendment](#amendments-modified-dependency-files), not through `src/`.

Open:

- File-system semantics of unit files: executable bits, symbolic links, binary
  content, line endings, paths that differ only in case, and paths reserved for
  Assemblr's own files. **OC-48.**

### `amendments/`: modified dependency files

`amendments/` holds modified **full-file copies** of files that dependencies
provide. Authors edit ordinary copies of files. They do not hand-write
low-level merge operations. Assemblr derives the changes. See
[amendments-and-composition.md](amendments-and-composition.md).

Open:

- The on-disk layout and naming of amendment copies, and where their provenance
  metadata is stored. **OC-3.**
