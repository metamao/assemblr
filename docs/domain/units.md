# Units

A unit is an author-owned, opinionated implementation of a software capability
or integration. Units may target web applications, infrastructure, native
applications, services, or any other software. Assemblr is technology-agnostic.

## Identity — Approved

The canonical form of a unit identity is:

```text
@owner/unit-name
```

Examples:

```text
@metamao/node
@metamao/cloudflare-worker
@metamao/cloudflare-angular-ssr
@metamao/d1-drizzle
@alice/cloudflare-angular-ssr
```

Rules:

- The owner is mandatory.
- An owner may represent an individual or an organization.
- Unit names use lowercase ASCII letters, digits, and hyphens. Owners follow
  the same convention.
- Each segment, owner and unit name, is non-empty, begins and ends with a
  letter or digit, and contains no consecutive hyphens. For example, `-node`,
  `node-`, and `cloud--worker` are malformed.
- An identity is exactly `@`, the owner, `/`, and the unit name, with nothing
  else.
- A malformed identity is rejected with a validation error. It is never
  normalized, for example by lowercasing.
- There is no identity-specific length limit.
- Owner and unit name **together** determine identity.
  `@metamao/cloudflare-angular-ssr` and `@alice/cloudflare-angular-ssr` are
  different units. Neither is official or privileged.
- The unit's own manifest supplies its identity. Registries and repository
  locations do not.
- Identity does **not** imply dependencies. A unit declares its dependencies
  explicitly (see [dependencies.md](dependencies.md)).
- Do not infer repository layout, dependency structure, or relationships
  between units from owners or names. For example, `cloudflare-angular-ssr`
  does not imply a dependency on `cloudflare-worker`.
- The owner namespace is not necessarily tied permanently to a GitHub identity.
- Authentication and verification of namespace ownership are **not required in
  Alpha**.

## Versioning — Approved

- Unit versions use SemVer.
- The manifest declares the unit's **exact** version.
- Dependency declarations may use SemVer **ranges**.
- Resolution and lock state record **exact** versions.
- Each published version is a Git tag, `v<version>`, whose manifest declares
  exactly that version (see
  [registries-and-discovery.md](registries-and-discovery.md#units-are-git-repositories--approved)).
- Published versions are immutable (see
  [authoring-workflow.md](authoring-workflow.md#publication--approved)).
- A unit's published versions are unique ignoring build metadata. Two versions
  that differ only in build metadata, such as `1.0.0+a` and `1.0.0+b`, are
  ambiguous, and Assemblr never prefers one of them because of its metadata
  (see
  [dependencies.md](dependencies.md#pre-releases-and-build-metadata--approved)).

Requirements use Cargo's SemVer requirement syntax and semantics, with an
operator on every comparator, such as `^1.2.3`, `~1.2`, `=1.2.3`, or `>=1.2,
<1.5`; wildcards such as `*` and `1.*` count as one. A bare version such as
`1.2.3` is refused, because ecosystems disagree on its meaning: Cargo reads
it as `^1.2.3`, and npm, pip, and Poetry as exactly `1.2.3` (owner decision,
**OC-15** resolved).

Open:

- Whether publication, registration, or synchronization reject versions that
  differ only in build metadata before resolution reports them. **OC-25.**

## Authoring repository convention — Approved

Every unit is maintained in **its own Git repository**. This is a requirement,
not just an organizational convention: Git holds the history from which
published versions are identified and historical content is recovered.

- A repository holds exactly **one** unit, with `manifest.jsonc` at its root.
  Several independently published units never share a repository.
- Each unit has an independent publication lifecycle.
- Repositories may be private. The owner decides how they are hosted and
  organized.

A unit repository has this conceptual structure:

```text
manifest.jsonc        required
src/                  optional: files introduced by the unit
amendments/           optional: modified copies of dependency files
.gitignore            contains /build/
build/                generated by `unit build`, Git-ignored
manifest.schema.json  the manifest's JSON Schema for editor support, written by `unit init`, tracked
README.md             optional: the unit's description for people, scaffolded by `unit init`
AGENTS.md             optional: instructions for coding agents, scaffolded by `unit init`
assemblr-lock.json    the unit lockfile: CLI-managed, tracked, resolved versions
```

- `manifest.jsonc` is required.
- The unit lockfile is described in
  [authoring-workflow.md](authoring-workflow.md#unit-lock-state--approved).
- `src/` and `amendments/` are each optional. Do not require empty directories
  just for uniformity.
- The initialized scaffold supports editing the manifest with JSON Schema
  (see [manifest.md](manifest.md#editor-support--approved)).

The generated local manifest schema is `manifest.schema.json` at the top
level, tracked (**OC-17**, resolved; D-2); see
  [authoring-workflow.md](authoring-workflow.md#initialization-details--provisional-d-5-d-33).

## Unit contents — Approved

### `src/`: unit files

`src/` holds the files the unit introduces. All files in `src/` follow the
same conceptual lifecycle. There are **no** author-facing file classes such as
the former `derived` and `scaffold` distinction, and they must not be
reintroduced.

Every unit file is delivered byte for byte: Assemblr never renders or
substitutes anything in it. A value each project sets stays in the file as
a declared **placeholder** that the consumer replaces (see
[placeholders.md](placeholders.md)).

In a consumer project, files delivered from `src/` are starting points that
the consumer may modify. They are reconciled like every other contribution
(see [consumer-projects.md](consumer-projects.md#file-contributions--approved)).

File paths:

- A unit file's path is relative to `src/`, with segments separated by `/`.
- Paths are validated the same way on every platform, so a unit is accepted
  or rejected the same way everywhere. Assemblr prefers predictable, portable
  paths to accepting every name the current file system supports.
- A path is rejected, never normalized, when:
  - it is empty, or starts with `/`;
  - it contains `\` or a NUL character;
  - a segment is empty, `.`, or `..`;
  - a segment contains `:`, which Windows reads as a drive prefix or an
    alternate data stream;
  - a segment ends with `.` or a space, which Windows removes;
  - a segment is a device name Windows reserves (`CON`, `PRN`, `AUX`, `NUL`,
    `COM0` to `COM9`, `LPT0` to `LPT9` and their superscript-digit forms,
    `CONIN$`, `CONOUT$`), in any case and with any extension, such as
    `nul.txt`.

Path collisions:

- If two different units in one composition deliver a file at the same path
  from their `src/` directories, composition fails with an explicit **path
  collision** error that names both units and the path.
- This holds whether the units are independent or one depends on the other.
  Neither unit wins by declaration order, dependency order, or any other
  priority, and the two files are never merged automatically.
- A unit that needs to modify a file a dependency provides does so through an
  [amendment](#amendments-modified-dependency-files), not through `src/`.
- A path cannot be both a file and a directory. A file whose path is a
  directory of another file's path, such as `config` and `config/app.json`,
  is a path collision too.
- Collisions are detected the same way within one unit's files and across the
  files of several units.
- Paths that differ only in case, such as
  `README.md` and `readme.md`, also collide, and the file-or-directory check
  ignores case too, because a case-insensitive file system would otherwise
  lose one of the files silently (**OC-48**).
- Paths that differ only in Unicode normalization also collide, alone or
  combined with differences in case, because some file systems do not keep
  them apart either. A precomposed `é` and an `e` followed by a combining
  acute accent therefore collide, as do `É` and `é`.
- Precisely, two paths collide when they are equal after this comparison
  key: decompose the path canonically (NFD); map each character to its
  lowercase and then to its uppercase, each step only when the mapping is a
  single character; and decompose canonically again. This is not Unicode's
  canonical caseless matching, which uses full case folding and maps some
  characters to several, such as `ß` to `ss`. Case-insensitive file systems
  compare one character to one character, so:
  - `ß` and `ss`, `ﬁ` and `fi`, and `İ` and `i` do not collide;
  - `ς` and `σ`, `µ` and `μ`, `ſ` and `s`, and `ı` and `i` collide, as NTFS
    equates them, although lowercasing alone keeps them apart;
  - compatibility equivalents, such as the ligature `ﬁ` and `fi`, do not
    collide, as file systems keep them apart.

Open:

- File-system semantics of unit files: executable bits and symbolic links
  beyond what `unit build` reads from a working tree (see
  [build details](authoring-workflow.md#build-details--approved)), binary
  content, line endings, the provisional case rule above, and paths reserved
  for Assemblr's own files. **OC-48.**

### `amendments/`: modified dependency files

`amendments/` holds modified **full-file copies** of files that dependencies
provide. Authors edit ordinary copies of files. They do not hand-write
low-level merge operations. Assemblr derives the changes. See
[amendments-and-composition.md](amendments-and-composition.md).

- An amendment targets a file that a unit **below** it, a direct or
  transitive dependency, provides in its `src/`.
- The copy lives at `amendments/<path>`, where `<path>` is the file's path in
  that dependency's `src/`, under the same path rules. The unit's own `src/`
  must not hold the same path.
- An amendment changes a file's content only. It never deletes or renames a
  file, and never changes its executable bit.
- Each amendment is declared in the manifest's `amendments` map, under its
  path, with the dependency's identity and the exact base version (see
  [manifest.md](manifest.md#serialization-of-dependencies-placeholders-and-amendments--approved)).
  A copy that is not declared, and a declaration without a copy, are both
  errors: an undeclared copy has no base.
- `unit amend` creates the copy and the declaration (see
  [authoring-workflow.md](authoring-workflow.md#amend--approved)).
