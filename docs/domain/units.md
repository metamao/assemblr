# Units

A unit is an author-owned, opinionated implementation of a software capability
or integration. Units may target web applications, infrastructure, native
applications, services, or any other software. Assemblr is technology-agnostic.

## Identity — Approved

The canonical form of a unit identity is:

```text
@owner/unit-name
```

Examples:

```text
@metamao/node
@metamao/cloudflare-worker
@metamao/cloudflare-angular-ssr
@metamao/d1-drizzle
@alice/cloudflare-angular-ssr
```

Rules:

- The owner is mandatory.
- An owner may represent an individual or an organization.
- Unit names use lowercase ASCII letters, digits, and hyphens.
- Owner and unit name **together** determine identity.
  `@metamao/cloudflare-angular-ssr` and `@alice/cloudflare-angular-ssr` are
  different units. Neither is official or privileged.
- The unit's own manifest supplies its identity. Registries and repository
  locations do not.
- Identity does **not** imply dependencies. A unit declares its dependencies
  explicitly (see [dependencies.md](dependencies.md)).
- Do not infer repository layout, dependency structure, or relationships
  between units from owners or names. For example, `cloudflare-angular-ssr`
  does not imply a dependency on `cloudflare-worker`.
- The owner namespace is not necessarily tied permanently to a GitHub identity.
- Authentication and verification of namespace ownership are **not required in
  Alpha**.

Open:

- The character set and syntax rules for owners, and boundary rules for both
  segments (leading, trailing, or consecutive hyphens, length limits).
  **OC-14.**

## Versioning — Approved

- Unit versions use SemVer.
- The manifest declares the unit's **exact** version.
- Dependency declarations may use SemVer **ranges**.
- Resolution and lock state record **exact** versions.
- Published versions are immutable (see
  [authoring-workflow.md](authoring-workflow.md#publication--approved)).

Open:

- The SemVer range dialect and how pre-release and build metadata are treated.
  **OC-15.**

## Authoring repository convention — Approved

The preferred convention is **one Git repository per unit**. The owner decides
how unit repositories are grouped or organized locally.

A unit repository has this conceptual structure:

```text
manifest.jsonc        required
src/                  optional: files introduced by the unit
amendments/           optional: modified copies of dependency files
.gitignore            contains /build/
build/                generated by `unit build`, Git-ignored
<local manifest schema>  generated, offline JSON Schema for editor support
```

- `manifest.jsonc` is required.
- `src/` and `amendments/` are each optional. Do not require empty directories
  just for uniformity.
- The initialized scaffold supports editing the manifest with JSON Schema
  (see [manifest.md](manifest.md#editor-support--approved)).

Open:

- The file name and location of the generated local manifest schema, and
  whether it is tracked in Git. **OC-17.**

## Unit contents — Approved

### `src/`: unit files

`src/` holds the files the unit introduces. All files in `src/` follow the
same conceptual lifecycle. There are **no** author-facing file classes such as
the former `derived` and `scaffold` distinction, and they must not be
reintroduced.

Unit file contents may be customized by the unit's parameters through template
interpolation. Parameters never change file paths or file existence (see
[parameters-and-options.md](parameters-and-options.md#what-parameters-must-not-do--approved)).

Open:

- What happens when a `src/` file has the same path as a file a dependency
  provides. **OC-18.**

### `amendments/`: modified dependency files

`amendments/` holds modified **full-file copies** of files that dependencies
provide. Authors edit ordinary copies of files. They do not hand-write
low-level merge operations. Assemblr derives the changes. See
[amendments-and-composition.md](amendments-and-composition.md).

Open:

- The on-disk layout and naming of amendment copies, and where their provenance
  metadata is stored. **OC-3.**
